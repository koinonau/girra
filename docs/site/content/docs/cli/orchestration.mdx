Orchestration is Girra's structured multi-agent layer: a **Run** (namespace + coordinator inbox), **Tasks**, **Dispatches**, supervised **workers**, messages, and decision gates.

Use it when you need ownership, completion tracking, or a DAG. For one-off prompts, use `girra terminal send`. For full ownership handoffs without supervision, use worktree/terminal commands from the `orca-cli` skill.

<Callout title="Experimental">
  Enable orchestration under Settings → Experimental before using these commands. The CLI talks to
  the running Girra runtime, so `girra status --json` should succeed first.
</Callout>

<Callout title="Legacy commands retired">
  `girra orchestration run` and `run-stop` (and `coordinator-start` / `coordinator-stop`) perform
  **no effects**. They return recovery text pointing at `girra skills get orchestration --full`. Use
  the Run + worker-start flow below.
</Callout>

## Core model

- **Run** — durable namespace and home inbox. Never schedules or places workers.
- **Task** — a work item with a spec, dependencies, and status: `pending`, `ready`, `dispatched`, `completed`, `failed`, or `blocked`.
- **Dispatch** — one attempt of a task on a terminal; lifecycle authority for `worker_done` / heartbeat.
- **Message** — inbox mail (`status`, `dispatch`, `worker_done`, `escalation`, `question`, `heartbeat`, …).
- **Decision gate** — a coordinator-owned question that blocks a task until it is resolved.

Completion authority comes from the active dispatch context. Worker completion and heartbeat messages should include both `taskId` and `dispatchId`.

Task IDs printed in terminals, such as `task_...`, are clickable links. Clicking one asks the Girra runtime for the task's current dispatch and focuses the assigned terminal, including when the task lives in a remote or SSH runtime.

## Preferred supervised loop

```bash
girra orchestration run-create --objective "Split checkout QA and summarize blockers" --json
girra orchestration task-create --spec "Audit billing settings for mobile layout" --task-title "Billing audit" --json
girra orchestration worker-start --task <taskId> --worktree current --agent claude --json
# or new worktree:
girra orchestration worker-start --task <taskId> --worktree new-child --name billing-audit --agent claude --setup run --json
# optional per-worker model / effort (Claude only; not with --terminal):
girra orchestration worker-start --task <taskId> --worktree current --agent claude --model <opaque-model-id> --effort high --json
```

`--model` accepts opaque provider model IDs for Claude. `--effort` requires `--model` and only applies when that agent/model supports the level. Neither flag can combine with `--terminal` (reuse an existing pane). Overrides apply to that launch only and show under `launch.requested` / `launch.effective` in the start receipt. Federated starts need a worker host that advertises launch-preference support.

Wait for completions (process every message in a Delivery, then ack):

```bash
girra orchestration check --wait --types worker_done,escalation,question --timeout-ms 900000 --json
girra orchestration check --ack <deliveryId> --wait --types worker_done,escalation,question --timeout-ms 900000 --json
```

Worker completion (from the worker pane; include injected IDs):

```bash
girra orchestration send \
  --type worker_done \
  --subject "Completed mobile audit" \
  --body "Fixed footer overlap; no follow-ups." \
  --task-id <taskId> \
  --dispatch-id <dispatchId> \
  --outcome succeeded \
  --files-modified "src/app/settings/Billing.tsx" \
  --json
```

`worker_done` requires `--outcome succeeded|failed`.

Inspect / recover:

```bash
girra orchestration worker-show --dispatch <dispatchId> --json
girra orchestration worker-read --dispatch <dispatchId> --limit 50 --json
girra orchestration worker-stop --dispatch <dispatchId> --json
# After an accepted worker_done: reuse the same terminal for a follow-up Dispatch, or release it
# (archives inspectable output, then closes only that coordinator-owned agent terminal):
girra orchestration worker-release --dispatch <dispatchId> --json
# Keep a settled worker live for debugging when the user asked to retain it:
girra orchestration worker-retain --dispatch <dispatchId> --json
# retry placement is explicit — --retry-of does not inherit --on/worktree:
girra orchestration worker-start --task <taskId> --retry-of <dispatchId> --worktree current --agent claude --json
```

Do not leave completed worker terminals open just to re-read output — use `worker-read` after `worker-release`. Do not substitute a broad `terminal close` when release returns `release_pending` or `release_unknown`; follow the receipt's recovery action.

## Federated workers (optional)

```bash
girra orchestration worker-start \
  --task <taskId> \
  --on windows \
  --worktree new-top-level \
  --repo <exact_remote_repo_selector> \
  --name remote-worker \
  --agent claude \
  --setup run \
  --json
girra orchestration send --to dispatch:<dispatchId> --subject "Follow-up" --body "…" --json
```

Later commands route by Dispatch ID; do not repeat `--on`.

## Low-level dispatch (custom topology)

```bash
girra worktree create --name billing-audit --agent claude --json
girra terminal wait --terminal <workerHandle> --for tui-idle --timeout-ms 60000 --json
girra orchestration dispatch --task <taskId> --to <workerHandle> --inject --json
```

## Messaging notes

- Default `check` is the bound Run's oldest unacked Delivery (FIFO). Replay until `--ack`.
- `--peek` / `--all` do not consume mail.
- Group addresses: `@all`, `@idle`, `@claude`, `@opencode`, `@worktree:<id>` — never for `worker_done` / heartbeat.
- Every group except `@worktree:<id>` means the live Dispatches of the sender's own Run, delivered to their Dispatch mailboxes (or child Run mailboxes for nested coordinators). A sender in no Run is refused; `--run` must match the audience and never grants membership.
- Run groups exclude their owning coordinator. A worker raising a blocker sends to `run:<id>`. `@worktree:<id>` includes coordinators in that workspace.
- Quote PowerShell group addresses: `--to "@all"`.

```bash
girra orchestration send --to @all --subject "Heads up" --body "Pausing dispatches for a review." --json
girra orchestration send --to @idle --subject "Anyone free?" --json
girra orchestration send --to @claude --subject "Claude workers in this Run only" --json
```

While a wait is active, the CLI emits small JSON heartbeat lines to stderr every 15 seconds. Stdout remains the final command result.

## Worker contract

Dispatched workers receive a preamble that tells them how to communicate with the coordinator:

- Send `worker_done` exactly once, even on failure, with `--outcome`.
- Include a short `--body` summary: what was done, what was found, and what remains.
- Include both task and dispatch IDs so stale retries cannot complete the wrong dispatch.
- Send `heartbeat` messages during long active work.
- Use `girra orchestration ask` for blocking questions instead of local TUI prompts.

```bash
girra orchestration ask \
  --to <coordinatorHandle> \
  --question "Should I update the shared component or only this page?" \
  --options "shared,page-only" \
  --timeout-ms 600000 \
  --json
```

With `--json`, `ask` prints the standard `{id, ok, result, _meta}` envelope, so workers read the answer with `jq -r .result.answer`.

## Decision gates

Use `ask` for worker-to-coordinator questions. Use explicit gates when the coordinator has created a task DAG and wants to block a task until a decision is recorded:

```bash
girra orchestration gate-create \
  --task <taskId> \
  --question "Merge the shared button change into the task branch?" \
  --options '["yes","no"]' \
  --json

girra orchestration gate-resolve --id <gateId> --resolution "yes" --json
```

## Recovery

```bash
girra orchestration dispatch-show --task <taskId> --json
girra orchestration dispatch-show --task <taskId> --preamble --json
girra orchestration task-list --json
girra orchestration task-update --id <taskId> --status blocked --result '{"reason":"waiting on credentials"}' --json
```

Reset only when you are intentionally abandoning orchestration state:

```bash
girra orchestration reset --tasks --json
girra orchestration reset --messages --json
girra orchestration reset --all --json
```

`reset` affects runtime-global orchestration state. Do not run it while another coordinator is active unless that is the intended cleanup.

## Choosing the right command

Use `girra terminal send` for a lightweight prompt to an agent you are watching.

Use `girra orchestration worker-start` (or `dispatch --inject`) when a worker must report `worker_done`, ask questions through the coordinator, and be tracked by task ID.

Use `girra orchestration run-create` + tasks + workers when you want a durable Run namespace and supervised multi-agent loop — not the retired `orchestration run` command.
