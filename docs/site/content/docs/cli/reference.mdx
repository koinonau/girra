The `girra` CLI talks to a running Girra runtime. Use it when a shell script or agent needs to inspect worktrees, launch terminals, open files, automate the built-in browser, or report progress back into Girra.

## Verify the runtime

Register the CLI under [Settings → General → Girra CLI](/docs/settings), then check that it can reach Girra.

```bash
command -v girra
girra status --json
```

<Callout title="Hosts installed before the rename">
  The CLI is `girra` on every platform. Installs predating the rename answer to `orca` as well, and
  on Linux to `orca-ide`; both stay as aliases. Do not check for the CLI with `command -v orca` on a
  GNOME desktop, where that resolves to the GNOME Orca screen reader at `/usr/bin/orca`.
</Callout>

If Girra is not already running:

```bash
girra open --json
girra status --json
```

Use `--json` when another tool will parse the result. Human-readable output is for quick terminal checks.

## Selectors

Most commands accept selectors instead of requiring long IDs:

```bash
girra repo show --repo id:<repoId> --json
girra worktree show --worktree active --json
girra worktree show --worktree path:/abs/path/to/worktree --json
girra worktree show --worktree branch:feature-name --json
girra worktree show --worktree issue:123 --json
```

`active` and `current` resolve to the enclosing Girra-managed worktree from the shell's current directory or terminal context. Use explicit selectors in scripts that may run outside the target worktree. For remote runtimes, prefer full server-side selectors such as `id:<repoId>::<absolute-worktree-path>` or `path:<absolute-server-path>` because the local shell's current directory may not exist on the runtime host.

## Choose a host

List every machine the current Girra host can target and the selector for each one:

```bash
girra host list --json
```

The result includes this machine, its registered [SSH targets](/docs/ssh), and paired [Remote Girra Servers](/docs/remote-servers). Use `--host local` for this machine, `--host ssh:<target-id>` for an SSH target, and `--environment <server-name>` for a paired server. SSH rows include the detected remote platform (`linux`, `darwin`, or `win32`) after the target connects; older or disconnected targets report `platform unknown`. They also include `connected` and, when known, the SSH lifecycle `connectionStatus`. SSH labels and paired-server names also resolve when they are unique; use the IDs from `host list` when names collide. If you put a machine name on the wrong selector, Girra reports the matching machine and the flag to use instead of returning an empty result.

## Runtime commands

```bash
girra open --json
girra status --json
girra serve --port 6768 --pairing-address 100.64.1.20 --json
```

`girra serve` starts a runtime server in the foreground without opening the desktop window. Use it for [Remote Girra Servers](/docs/remote-servers) or headless environments, and stop it with `Ctrl-C`.

## Repos

```bash
girra repo list --json
girra repo add --path /abs/path/to/repo --json
girra repo show --repo id:<repoId> --json
girra repo set-base-ref --repo id:<repoId> --ref origin/main --json
girra repo search-refs --repo id:<repoId> --query main --limit 10 --json
```

Set the repo base ref before creating lots of worktrees so new tasks branch from the right place by default.

## Worktrees

```bash
girra worktree list --repo id:<repoId> --json
girra worktree ps --json
girra worktree current --json
girra worktree show --worktree active --json
girra worktree create --repo id:<repoId> --name fix-login --json
girra worktree create --name child-task --agent claude --prompt "Investigate the flaky login test" --json
girra worktree set --worktree active --comment "reproduced failure; testing token refresh fix" --json
girra worktree rm --worktree id:<worktreeId> --force --json
```

When `worktree create` runs from inside a Girra-managed worktree, Girra records the new worktree as a child when it can infer the relationship. Pass `--parent-worktree active` to be explicit, or `--no-parent` when the new work is independent.

Agent startup flags:

```bash
girra worktree create --name review-api --agent claude --setup run --json
girra worktree create --name quick-check --agent claude --prompt "Summarize the diff" --setup skip --json
girra worktree create --name hidden-setup --setup inherit --json
```

`--agent` launches the selected agent in the first terminal. `--prompt` sends initial work to that agent. `--setup run|skip|inherit` controls repo setup hooks; `inherit` follows the repo policy.

## Terminals

```bash
girra terminal list --worktree active --json
girra terminal show --terminal <handle> --json
girra terminal read --terminal <handle> --json
girra terminal read --terminal <handle> --screen --json
girra terminal read --terminal <handle> --cursor <cursor> --limit 1000 --json
girra terminal send --terminal <handle> --text "continue" --enter --json
girra terminal wait --terminal <handle> --for tui-idle --timeout-ms 300000 --json
girra terminal create --worktree active --title "tests" --command "npm test" --json
girra terminal split --terminal <handle> --direction horizontal --command "npm run dev" --json
girra terminal rename --terminal <handle> --title "runner" --json
girra terminal switch --terminal <handle> --json
girra terminal close --terminal <handle> --json
girra terminal close --worktree active --all --json
```

Omit `--terminal` to target the active terminal in the current worktree. Read before sending when you are not sure what the terminal is waiting for.

Close stops the process as part of removing the terminal. Use `--terminal <handle>` for one
terminal, or `--worktree <selector> --all` to durably close every terminal in exactly that
workspace, including its saved layouts and agent-resume records. Use workspace Sleep when those
terminals should resume later. If the execution host cannot confirm that every PTY stopped, bulk
close returns a failing `unverifiable` result rather than claiming the processes exited.
`terminal stop` remains only for compatibility with older tooling.

<Callout title="Terminal handles">
  Terminal handles are runtime-scoped. If Girra restarts or a command reports a stale terminal
  handle, run `girra terminal list --json` and reacquire the handle.
</Callout>

`terminal list` reports each terminal's `executionHostId` when Girra can verify it, plus a result-level `hostScope` with covered and omitted host IDs. Treat a missing host identity or scope as **unverifiable**, not local. A missing terminal is evidence that it exited only when its execution host is listed in `hostScope.hostIds`.

By default, `terminal read` returns the accumulated output stream with terminal escapes stripped. Programs that redraw lines can therefore appear as stacked fragments. Use `--screen` when you need the currently rendered frame; the response's `source` identifies `stream`, `screen`, or `screen-unavailable`. Screen reads have no history to page, so `--screen` and `--cursor` are mutually exclusive.

For long output, use cursor reads. Save `nextCursor` from one stream read, then pass it back with `--cursor` to fetch only new output.

## Files

```bash
girra file open src/App.tsx --worktree active --json
girra file diff src/App.tsx --staged --worktree active --json
girra file open-changed --mode both --worktree active --json
```

Paths are relative to the selected worktree. `open-changed` reads git status and opens changed files in edit, diff, or both modes.

## Built-in browser

Browser commands control Girra's embedded browser tab for the selected worktree. They do not control Chrome, Safari, or the Girra desktop UI.

Use a snapshot -> act -> snapshot loop:

```bash
girra goto --url http://localhost:3000 --worktree active --json
girra snapshot --worktree active --json
girra click --element @e3 --worktree active --json
girra fill --element @e1 --value "user@example.com" --worktree active --json
girra wait --text "Welcome" --worktree active --json
girra screenshot --worktree active --json
```

Refs such as `@e3` come from `snapshot`. Re-snapshot after navigation, tab switches, clicks that change the page, and any stale-ref error.

Tab and capture commands:

```bash
girra tab list --worktree active --json
girra tab create --url http://localhost:3000 --worktree active --json
girra tab switch --index 1 --worktree active --json
girra capture start --worktree active --json
girra console --limit 50 --worktree active --json
girra network --limit 50 --worktree active --json
girra full-screenshot --worktree active --json
girra pdf --worktree active --json
```

Use `girra exec --command "<agent-browser command>" --json` only for browser actions that do not have a typed Girra command yet.

Browser device emulation:

```bash
girra set device --name "iPhone 12" --worktree active --json
girra screenshot --worktree active --json
```

## Desktop computer use

Use `girra computer` for native desktop apps outside the built-in browser:

```bash
girra computer permissions --json
girra computer list-apps --json
girra computer get-app-state --app com.apple.Safari --json
girra computer click --app com.apple.Safari --element-index 12 --json
girra computer paste-text --app com.apple.Safari --text "hello" --json
```

See [Computer use](/docs/cli/computer-use) for the full workflow and permission setup.

## Mobile emulator

The mobile emulator commands control iOS Simulator devices through Girra's worktree-scoped bridge. Use them instead of raw `serve-sim` or `simctl` when an agent is operating from inside Girra, so lifecycle and active-device state stay attached to the current worktree.

```bash
girra emulator list --worktree active --json
girra emulator attach "<device-name-or-udid>" --worktree active --json
girra emulator tap 0.5 0.7 --worktree active --json
girra emulator type "hello" --worktree active --json
girra emulator gesture '[{"type":"begin","x":0.5,"y":0.8},{"type":"move","x":0.5,"y":0.4},{"type":"end","x":0.5,"y":0.2}]' --worktree active --json
girra emulator button home --worktree active --json
girra emulator rotate landscape_left --worktree active --json
girra emulator exec --command "tap 0.5 0.7" --worktree active --json
girra emulator kill --worktree active --json
girra emulator shutdown --worktree active --json
```

Coordinates are normalized from `0` to `1`. Prefer `tap` for single taps, and use `gesture` for drags or multi-step touch input. Pass `--device <udid-or-name>` or `--emulator <id>` when a script must target a specific simulator instead of the worktree's active emulator.

## Linear

The `girra linear` surface is what agents use via the `orca-linear` skill (legacy install name `linear-tickets` still works). Prefer `--json`. Linked worktrees resolve with `--current`.

### Read

```bash
girra linear issue --current --full --json
girra linear issue ENG-123 --comments --children --relations --activity --json
girra linear search "auth bug" --workspace all --json
girra linear list --filter assigned --limit 10 --json
girra linear list-issues --team ENG --state started --assignee me --json
girra linear list-issues --query auth --updated-at -P7D --cursor <cursor> --workspace <id> --json
girra linear team list --json
girra linear team states --team ENG --json
girra linear team labels --team ENG --json
girra linear project list --query launch --json
```

`--full` expands comments, children, attachments, relations, and activity. Section flags (`--comments`, `--children`, `--attachments`, `--relations`, `--activity`) work individually.

### MCP-style write

```bash
# Create or update (omit id/--current to create; requires --team and --title on create)
girra linear save-issue --team ENG --title "Fix auth" --priority high --json
girra linear save-issue ENG-123 --state "In Progress" --assignee me --json
girra linear save-issue --current --project null --due-date null --json

girra linear relation add ENG-1 --related ENG-2 --type blocks --json
girra linear relation remove ENG-1 --related ENG-2 --type related --json
```

`save-issue` labels **replace** the full label set (Linear MCP `save_issue` semantics). Literal `null` clears assignee, estimate, due date, project, or parent.

### Field helpers (still valid)

```bash
girra linear status set --current --to "In Progress" --json
girra linear assignee set --current --me --json
girra linear priority set ENG-123 --to high --json
girra linear estimate set --current --to 3 --json
girra linear due-date set --current --to 2026-08-01 --json
girra linear label add --current --label backend --json
girra linear comment add --current --body "Investigating regression" --json
girra linear attach --current --url https://example.com/repro --title "Repro" --json
girra linear create --title "Flaky login test" --team ENG --priority high --json
```

Run `girra linear --help` or `girra skills get orca-linear` for the version-matched list. Pass an explicit issue id (e.g. `ENG-123`) when a script may run outside a Girra-linked worktree.

## Skills (local, no runtime required)

List bundled guides, print a version-matched guide, or install/update hybrid skill packages without the desktop Settings UI:

```bash
girra skills list
girra skills get orca-cli
girra skills get orchestration --references
girra skills get orchestration --reference recovery-and-cleanup
girra skills get orchestration --full
girra skills install --skill orca-cli --skill orchestration
girra skills install --all --dry-run
girra skills update --all
```

`install` / `update` shell out to the same `npx skills` commands Settings uses. They do not contact the Girra runtime. See [Girra skills](/docs/cli/skills#keep-skills-up-to-date).

## Account (host-local runtime)

On a headless host running Girra (`girra serve` or the desktop app), add managed Claude accounts when the remote client cannot use **Add account** (remote runtime scope disables that button):

```bash
girra account list
girra account add
```

`account add` runs `claude login` in **this** terminal on the host, then registers the captured credentials with the local runtime. Run these on the machine that owns the accounts, not through a client-only remote session.

## Artifacts

Publish HTML or Markdown through the signed-in Girra account. Viewing a public link does not require sign-in; create/list/update/delete do. **Publishing is off by default** — a human must enable **Settings → Artifacts → Allow publishing public artifact links** on the device. There is no CLI flag that grants the gate. `list`, `unshare`, and `delete` stay available so you can audit or revoke links after turning publishing off.

```bash
girra artifacts share ./report.html --json
girra artifacts share ./notes.md --json
girra artifacts update ./notes.md --json
girra artifacts unshare ./notes.md --json
girra artifacts list --json
girra artifacts list --cursor <cursor> --json
girra artifacts delete <id> --json
```

- Accepted files: `.html`, `.htm`, `.md`, `.markdown`.
- `share` stores the edit token in the active Girra profile and does not print it. `update` / `unshare` resolve by the same local path and profile that originally shared the file.
- `list` is paged (`nextCursor` → `--cursor`). `delete` takes the artifact id from `list` and does not need the original file.
- Relative HTML assets are not uploaded — share self-contained HTML or absolute asset URLs.
- Denied publish/update fails with `artifact_sharing_disabled`; fix Settings instead of retrying.
- Desktop: open a local HTML or Markdown file and use **Share as artifact**, or manage links from the sidebar **Artifacts** page.

## Automations, environments, and hooks

Scheduled prompts:

```bash
girra automations list --json
girra automations create --name "Daily review" --trigger daily --time 09:00 --prompt "Review open changes" --provider claude --repo id:<repoId> --disabled --json
girra automations run <automationId> --json
```

Remote runtime environments:

```bash
girra environment add --name work-laptop --pairing-code "orca://pair?code=..." --json
girra environment list --json
girra environment rm --environment <selector> --json
```

Agent status hooks:

```bash
girra agent hooks status --json
girra agent hooks on --json
girra agent hooks off --json
```

## Agent habits

- Prefer `--json` for automation and agent calls.
- Prefer selectors over parsing UI labels.
- Read terminal state before sending input unless the next input is obvious.
- Use worktree comments for progress checkpoints. See [Worktree checkpoints](/docs/cli/worktree-checkpoints).
- Use [Orchestration](/docs/cli/orchestration) for tracked multi-agent dispatches instead of ad hoc terminal prompts.
